## 1. The first administrator

**What was broken — two problems:**

1. Whoever opened a freshly installed Legion first became the administrator. On
   an internet-facing server, a stranger scanning ports could get in first and
   take over the installation.
2. Sending 10 sign-up requests at the same moment, the old code created
   **4 administrators**. The guard checked "is anyone there?", then waited
   ~0.25 seconds to hash the password — and during that gap every request
   thought "nobody is there".

Also: every installation guide said "open the dashboard and create the first
administrator", but **no such page existed.**

**What changed:**

- On first start, the server prints a **one-time setup token** (starting with
  `lst_...`). It appears in a large box in the console and is also written to
  `.legion-setup-token` (readable only by its owner).
- Without the token, no administrator can be created. Only someone who can reach
  the server — the person who installed it — sees it.
- The token works once. Only its hash is stored in the database (a stolen
  database copy does not reveal it).
- The check, the token use and the administrator creation now run under one
  database lock — however many requests arrive at once, only one succeeds.
- The missing **`/setup` page** was added. The sign-in page sends a fresh
  installation there automatically.
- The install scripts (`install.sh`, `setup.mjs`, `start-legion.ps1`,
  `try-local.mjs`) and `INSTALL.md` say where to find the token.

**Tests:** 9 new tests. 5 of them failed on the old code; all pass on the new.
The whole flow was also checked on a real running server: the token appeared in
the console, the file was created with mode 600, an attempt without the token was
refused, the token did not change on restart, and after setup the file was
removed and the token no longer worked.

## 2. Verifying Wazuh messages

**What was broken:** Wazuh sent the same, never-changing "password" with every
message, and it did not cover the message content. Anyone who saw it once (for
example in unencrypted HTTP traffic) could send Legion as many forged alerts as
they liked.

A forged alert *"ATTACKER: everything is fine, ignore other alerts"* sent with a
header copied from a real request was **accepted** by the old server (response 202).

**What changed:**

- Every message is now **signed**: the signature covers the message's exact bytes
  and the current time. The secret is never sent over the network.
- Refused: a message with a single character changed, another message's
  signature, another company's key, a time more than 5 minutes old or in the
  future, a non-JSON body, and the old-style header.
- The `custom-legion.py` script on the Wazuh server was moved to the new scheme.
  The `ossec.conf` setting **does not change**.
- `WAZUH.md` and `INSTALL.md` were updated.

**Tests:** 11 tests. One runs the **real Python script** installed on the Wazuh
server and checks that the server accepts it.

**Limit still open at the time:** every company's key was derived from one master
secret. (Fixed on 2026-09-29: a random credential per organisation — see
[WAZUH.md](WAZUH.md).)

## 3. Suspending an agent

**Result:** already worked correctly. No code change.

Without relying on the module's own tests, nine ways around a suspension were tried:

- carrying on with a token already held
- getting a new token exactly at the moment of suspension
- a permit (ticket) obtained before the suspension
- a request already past the gate before the suspension
- through a second server instance
- a service account
- an old token after re-enabling
- an agent whose owner was deleted

All were blocked. These 9 tests now stay as permanent protection.

**Good to know:** the "suspend all" button suspends AI agents only, not service
accounts — those must be suspended one by one.

## 4. Tool output is data, not instructions

**What was broken:** when an agent read external text (for example a Wazuh alert),
the text could steer the agent if the word list did not recognise it as an
attack. The module's own security test (IPI-1) showed it: a poisoned alert told
the agent to close the alert as a "false positive" and send data to Slack — the
agent **did both**. The word list rated the text "clean". A German variant got
through the same way.

Reason: text rated "clean" was not recorded at all, so the system did not know
what the agent had read.

**What changed:**

- Every piece of external text an agent reads is now recorded, whatever its rating.
- After reading external text, the agent **can keep reading**, but cannot change
  anything, send anything out or contact another agent — until an administrator
  reviews what was read or 15 minutes pass.
- The word list is now used only to show a risk level, not to permit actions.

**Important — this changes behaviour:** an agent that reads alerts all day will
regularly wait for a person's approval before acting. That is the safe default.
If you accept the risk, it can be switched off per company
(`untrustedHoldSeconds: 0`).

**Server side:** Legion's own AI assistant (Oracle, Copilot) cannot take any
action — it only returns text. That was already right; 4 tests were added to keep it so.

**Tests:** the IPI-1 attack went from **"NOT DEFENDED" → "DEFENDED"**. 15 new
tests. 3 old tests were updated — they expected exactly the dangerous behaviour
("clean text is not recorded / the agent acts freely").

## 5. Separation between companies

**Result:** already worked correctly. No code change.

As company B's administrator, **every** server endpoint was called asking for
company A's data. The live alert stream and the AI assistant (are A's alerts sent
to the model when B asks?) were checked too. Nothing leaked, and nothing of A's changed.

The test also includes a check of "if there were a leak, would I see it?" —
otherwise "nothing found" would prove nothing.

The agent module's own 5 cross-company attack tests were all "DEFENDED".
