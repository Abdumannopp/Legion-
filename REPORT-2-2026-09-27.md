## 1. Notifications are no longer lost ✅

**The problem:** when a serious alert came from Wazuh, Legion sent an email — but
"fire and forget". If the mail server was down for a second, the alert stayed in
the database, but **nobody was notified** and nothing retried.

**Now:**
- The email is written to the database **at the same moment, in the same
  transaction** as the alert. If the alert exists, its notification exists — it
  cannot be otherwise.
- A separate worker sends it. If it fails, it **retries** after 30 seconds,
  1 minute, 2 minutes… (at most 1 hour apart).
- After 8 failed attempts it is marked "dead", and an administrator sees it
  (`GET /notifications/deliveries`) — it never disappears silently.
- A message is never sent twice.
- The error reason is kept, with **passwords and logins removed**.
- One company's message never goes to another.
- "Kill switch" notifications in the AI-agent module are now retried
  automatically too (previously nothing triggered them).

**Verified:** 23 new tests (success, failure, retry, permanent failure,
eventual success, no duplicates, no secrets, companies separated). Also tried on
a real running server: mail off — 3 attempts, marked "dead", **no** password in the log.

## 2. Stronger protection against tricking the AI ✅

**The problem found:** in Copilot, alert text an attacker can write was put in
the AI's **most trusted place** — inside the "system instruction". Like slipping
a stranger's letter in between the boss's orders.

**Now (server):**
- Alert text always sits in a separate place marked "untrusted data".
- A random boundary marker on every request — an attacker cannot know it in advance.
- Invisible characters (a person does not see them, the AI reads them) are removed.
- Useful information (IP, host name, log) is **not removed**.

**Now (agent module):** previously missed phrasings are detected, including in
**Russian and Uzbek**. Ordinary alerts stay "clean" (checked with 9 real logs).

**Result:** attack tests — previously 51 defended, 1 not defended, 4 partial.
Now **53 defended, 0 not defended, 3 partial**. The remaining 3 "partial" are not
about tricking the AI.

**Honest note:** a word list is never 100%. The main protection is that after
reading external text an agent cannot do anything serious until a person reviews
it (requirement 4 in the first report). These tests do not claim the AI is
"completely safe" — only that it resists the attacks tested.

## 3. Least privilege in the database ✅

**The problem:** when an AI agent sent an SQL query to the database, Legion read
the query text and refused dangerous ones (`tools/sql.ts`). But that was only
**text checking**. The single connection that ran the query was the database
**owner (superuser)**. So one mistake in the check, or a way around it, and the
agent could do anything. This was tried on a real database with that connection:
- a file on the server (`/etc/passwd`) was read,
- a table was created and dropped,
- **another company's data was visible**,
- the server configuration was reloaded.

Like giving a guard a list, and leaving him one key that opens every door.

**Now:** agent queries run as a **separate, restricted database user**. Only the
allowed tables are open to it; the rest are closed. The database **itself** now refuses:
- tables that are not allowed (passwords, sessions, the audit log),
- reading server files, running programs,
- creating or dropping tables, granting itself more rights,
- stopping other connections, changing server settings,
- **another company's rows** — even when the query has no condition at all, or
  deliberately names another company.

Also: on every start this user is reset to exactly the listed rights. If someone
grants extra rights by hand, they are **removed automatically** on the next
restart. The old text check (`tools/sql.ts`) is **unchanged** — it stands first,
the database second. Legion's own connection and other database users see no
change (a test proves that too).

**Verified:** 30 new tests, all on real PostgreSQL 16. Each sends the query
straight to the database without the text check — only the database itself may
catch it. To prove the tests really work, the code was **deliberately broken**:
- company separation removed → 7 tests failed,
- the agent given superuser rights → 15 tests failed,
- the bypass rule for other users removed → 1 test failed.

Then the code was restored and everything passed.

**Honest note:** this protection applies when agent SQL goes through
`tools.database()`. At the time, the agent module was not yet **wired** into the
Legion server. Once wired, the new user and password must be configured — step by
step in `packages/agent-identity/README.md`, "Database least privilege →
Production setup". Legion's own server connection was still a superuser at the
time — a separate matter for the server, not the agents.

## 4. Every security result is tied to an exact code version ✅

**The problem:** a result was recorded as "DEFENDED", but **on which code
version** was unknown. Old results mixed with new ones.

**Now every test run records:**
- the git commit (taken from the real code on the machine — it cannot be typed by hand)
- whether there are uncommitted changes
- the package version, a hash of the dependency list, the Node version
- start and end time
- each result tied to its own run

The validator **refuses** a result that is broken, incomplete, from another
commit or from uncommitted code. 27 tests.

## 5. Security tests can now stop a release ✅

**The problem:** the attack tests could never go "red", and CI did not run them at all.

**Now in CI:**
- A separate **"Security tests and attack assessment"** stage.
- **"Release gate"** — green only if every check passes.
- A release ships only if "Release gate" is green.

**A release is blocked when:** a security test fails; an attack gets through at
Critical/High severity; a required scenario is missing; the result file is broken
or incomplete; the result is from another commit or uncommitted code. If someone
adds `continue-on-error` to "turn red green", CI catches that too.

**Verified:** run end to end from a clean copy (server security tests 103, agent
security tests 156, 56 attacks — all passed). Then **deliberately broken**:
- webhook verification removed → 8 tests failed → release **stopped**
- 5 attack scenarios removed → "required scenarios missing" → **stopped**
- testing with uncommitted code → "not tied to a commit" → **stopped**

**One thing only the repository owner can do:** GitHub → Settings → Branches →
mark **"Release gate"** as required for `main`. CI can turn a check red, but it
cannot forbid a merge by itself.
