# Legion — 5 bosqichli ish hisoboti (sodda tilda)

**Sana:** 2026-09-27

Hujjatdagi **5 ta vazifaning hammasi bajarildi va tekshirildi**. (3-vazifa
dastlab to'xtab qolgan edi; keyinroq alohida bajarildi — pastda.)

Har bir o'zgarish alohida git commit sifatida saqlangan, shuning uchun
dasturchi har qatorni ko'ra oladi (`git log -p`).

---

## 1. Xabarnomalar endi yo'qolmaydi ✅

**Muammo edi:** Wazuh'dan jiddiy alert kelganda Legion email yuborardi — lekin
"yubordim-u, unutdim" usulida. Pochta serveri bir soniya ishlamay qolsa,
alert bazada turardi, lekin **hech kim xabar olmasdi** va hech kim qayta
urinmasdi.

**Endi:**
- Email alert bilan **bir vaqtda, bitta amalda** bazaga yoziladi. Alert bor
  bo'lsa, uning xabarnomasi ham bor — boshqacha bo'lishi mumkin emas.
- Alohida ishchi jarayon xabarni yuboradi. Yuborolmasa — 30 soniya, 1 daqiqa,
  2 daqiqa... (eng ko'pi 1 soat) kutib **qayta urinadi**.
- 8 marta urinib bo'lmasa, "dead" deb belgilanadi va administrator uni
  ko'radi (`GET /notifications/deliveries`) — jim yo'qolmaydi.
- Bitta xabar ikki marta yuborilmasligi uchun himoya bor.
- Xato sababi saqlanadi, lekin undagi **parol va login o'chiriladi**.
- Bir kompaniyaning xabari boshqasiga ketmaydi.
- AI agentlar modulidagi "kill switch" xabarlari ham endi avtomatik qayta
  yuboriladi (ilgari buni hech narsa ishga tushirmasdi).

**Tekshirildi:** 23 ta yangi test (muvaffaqiyat, xato, qayta urinish, doimiy
xato, oxir-oqibat muvaffaqiyat, dublikat yo'q, sir yo'q, kompaniyalar
ajralgan). Haqiqiy ishlab turgan serverda ham sinaldi: pochta o'chiq —
3 marta urindi, "dead" bo'ldi, logda parol **yo'q**.

## 2. AI'ni aldashdan himoya kuchaytirildi ✅

**Topilgan muammo:** Copilot'da hujumchi yozishi mumkin bo'lgan alert matni
AI'ga **eng ishonchli joyga** — "tizim ko'rsatmasi" ichiga — qo'yilardi.
Bu xuddi begona xatni boshliqning buyrug'i orasiga tiqib qo'yishdek.

**Endi (serverda):**
- Alert matni doim alohida, "ishonchsiz ma'lumot" deb belgilangan joyda.
- Har so'rovda tasodifiy chegara belgisi — hujumchi uni oldindan bila olmaydi.
- Ko'zga ko'rinmaydigan belgilar (odam ko'rmaydi, AI o'qiydi) olib tashlanadi.
- Foydali ma'lumot (IP, host nomi, log) **o'chirilmaydi**.

**Endi (agent modulida):** avval o'tkazib yuborilgan so'zlashlar aniqlanadi,
jumladan **rus va o'zbek tillarida** ham. Oddiy alertlar esa "toza" qoladi
(9 ta real log bilan tekshirildi).

**Natija:** hujum testlari — ilgari 51 himoyalangan, 1 himoyalanmagan,
4 qisman. Endi **53 himoyalangan, 0 himoyalanmagan, 3 qisman**. Qolgan 3 ta
"qisman" AI'ni aldash bilan bog'liq emas.

**Halol eslatma:** so'z ro'yxati hech qachon 100% bo'lmaydi. Asosiy himoya —
agent tashqi matnni o'qigandan keyin inson ko'rmaguncha jiddiy ish qila
olmasligi (1-hisobotdagi 4-talab). Ushbu testlar AI'ni "to'liq xavfsiz"
demaydi — faqat sinalgan hujumlarga qarshi turishini ko'rsatadi.

## 3. Ma'lumotlar bazasida eng kam huquq ✅

**Muammo edi:** AI agent bazaga SQL so'rov yuborganda, Legion so'rov
matnini o'qib, xavflisini rad etardi (`tools/sql.ts`). Lekin bu faqat
**matnni tekshirish** edi. So'rovni bajaradigan yagona ulanish esa bazaning
**egasi (superuser)** edi. Ya'ni tekshiruvda bitta xato bo'lsa yoki kimdir uni
chetlab o'tsa, agent hamma narsani qila olardi. Buni haqiqiy bazada sinab
ko'rdik — o'sha ulanish bilan:
- serverdagi fayl (`/etc/passwd`) o'qildi,
- jadval yaratildi va o'chirildi,
- **boshqa kompaniyaning ma'lumoti ko'rindi**,
- server sozlamalari qayta yuklandi.

Bu xuddi qorovulga ro'yxat berib, hamma eshikni ochadigan bitta kalitni
qoldirishga o'xshaydi.

**Endi:** agent so'rovlari **alohida, cheklangan baza foydalanuvchisi**
bilan bajariladi. Unga faqat ruxsat berilgan jadvallar ochiq, qolgani
yopiq. Endi bazaning **o'zi** quyidagilarni rad etadi:
- ruxsat berilmagan jadvallar (parollar, sessiyalar, audit jurnali),
- server fayllarini o'qish, dastur ishga tushirish,
- jadval yaratish yoki o'chirish, o'ziga ko'proq huquq berish,
- boshqa ulanishlarni to'xtatish, server sozlamalarini o'zgartirish,
- **boshqa kompaniyaning qatorlari** — so'rovda umuman shart bo'lmasa ham,
  yoki shart ataylab boshqa kompaniyani ko'rsatsa ham.

Qo'shimcha: har ishga tushishda bu foydalanuvchi aynan ro'yxatdagi
huquqlarga qaytariladi. Kimdir qo'lda ortiqcha huquq bersa, keyingi
qayta ishga tushishda u **avtomatik olib tashlanadi**. Eski matn tekshiruvi
(`tools/sql.ts`) **o'zgarmadi** — u birinchi turadi, baza ikkinchi.
Legion'ning o'z ulanishi va boshqa baza foydalanuvchilari hech qanday
o'zgarishni sezmaydi (buni ham test isbotlaydi).

**Tekshirildi:** 30 ta yangi test, hammasi haqiqiy PostgreSQL 16'da. Har
biri so'rovni matn tekshiruvisiz, to'g'ridan-to'g'ri bazaga yuboradi —
himoyani faqat bazaning o'zi ushlashi kerak. Testlar haqiqatan ishlashini
isbotlash uchun kodni **ataylab buzdik**:
- kompaniyalarni ajratish o'chirildi → 7 test yiqildi,
- agentga superuser huquqi berildi → 15 test yiqildi,
- boshqa foydalanuvchilar uchun o'tish qoidasi o'chirildi → 1 test yiqildi.

Keyin kod asl holiga qaytarildi va hammasi o'tdi.

**Halol eslatma:** bu himoya agent SQL'i `tools.database()` orqali o'tganda
ishlaydi. Agent moduli hali Legion serveriga **ulanmagan** (bu avval ham
shunday edi). Ulanganda yangi foydalanuvchi va parolni sozlash kerak — bu
qadamma-qadam `packages/agent-identity/README.md` ichidagi "Database least
privilege → Production setup" bo'limida yozilgan. Legion serverining o'z
baza ulanishi hali ham superuser. Bu agentlarga emas, serverning o'ziga
tegishli alohida masala, shuning uchun bu vazifada o'zgartirilmadi.

## 4. Har bir xavfsizlik natijasi kodning aniq versiyasiga bog'landi ✅

**Muammo edi:** natija "HIMOYALANGAN" deb yozilardi, lekin **qaysi kod
versiyasida** — noma'lum edi. Eski natijalar yangilari bilan aralashib ketardi.

**Endi har bir sinov yozadi:**
- git commit (kompyuterdagi haqiqiy koddan olinadi — qo'lda yozib bo'lmaydi)
- kodda saqlanmagan o'zgarish bormi-yo'qmi
- paket versiyasi, kutubxonalar ro'yxatining xeshi, Node versiyasi
- boshlangan va tugagan vaqt
- har bir natija o'z sinoviga bog'langan

Tekshiruvchi (validator) buzilgan, chala, boshqa commit'dan yoki saqlanmagan
koddan olingan natijani **rad etadi**. 27 ta test.

## 5. Xavfsizlik testlari endi relizni to'xtata oladi ✅

**Muammo edi:** hujum testlari hech qachon "qizil" bo'lmasdi va CI ularni
umuman ishga tushirmasdi.

**Endi CI'da:**
- Alohida **"Security tests and attack assessment"** bosqichi bor.
- **"Release gate"** — barcha tekshiruvlar o'tsagina yashil bo'ladi.
- Reliz faqat "Release gate" yashil bo'lsa chiqadi.

**Reliz qachon bloklanadi:** xavfsizlik testi yiqilsa; hujum Critical/High
darajada o'tib ketsa; majburiy ssenariy yo'q bo'lsa; natija fayli buzilgan
yoki chala bo'lsa; natija boshqa commit'dan yoki saqlanmagan koddan bo'lsa.
Birov "qizilni yashil qilish" uchun `continue-on-error` qo'shsa — CI buni
ham ushlaydi.

**Tekshirildi:** toza nusxadan boshidan oxirigacha ishga tushirildi (server
xavfsizlik testlari 103, agent xavfsizlik testlari 156, 56 hujum — hammasi
o'tdi). Keyin **ataylab buzildi**:
- webhook tekshiruvi o'chirildi → 8 test yiqildi → reliz **to'xtadi**
- 5 ta hujum ssenariysi o'chirildi → "majburiy ssenariylar yo'q" → **to'xtadi**
- saqlanmagan kod bilan sinov → "commit'ga bog'lanmagan" → **to'xtadi**

**Faqat siz qila oladigan bitta ish:** GitHub → Settings → Branches →
`main` uchun **"Release gate"** ni majburiy (required) qilib belgilang. CI
tekshiruvni qizil qila oladi, lekin birlashtirishni o'zi taqiqlay olmaydi.
